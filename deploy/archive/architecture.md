# 媒体任务的事务与生命周期

## 为什么统一发送流程

原来的实时回调、手动接口和后台补发各自发送消息。实时回调持有入库事务，手动发送没有登记文件占用，后台租约结束又不等于 SDK 或 CLI 上传已经结束。只在这些入口分别判断状态，会不断漏掉另一条路径。

现在以 `tg_forward_record` 作为发送任务及结果的唯一记录。实时监听、断线补采、晚到相册成员和手动转发都调用 `TelegramForwardService.enqueue`，没有其他媒体发送入口。主动对话框的纯文本发送保留现有同步接口；它不涉及采集消息或本地文件。

```mermaid
flowchart LR
    A[实时监听 / 补采 / 手动转发] --> B[短事务：消息、素材引用、发送任务]
    B --> C[提交]
    C --> D[执行器：领取任务并复制普通数据]
    D --> E[释放数据库事务]
    E --> F[登记实际文件操作]
    F --> G[Telegram / 云端 / 本地磁盘]
    G --> H[短事务：校验租约并保存结果]
    H --> I[释放实际文件占用]
```

## 必须保持的约束

1. **提交消息和发送任务是同一个事务。** 入库失败不能留下可发送任务，任务入库失败也不能吞掉异常并推进补采游标。
2. **网络发送不持有数据库会话。** `prepare` 只查询、验证并复制普通数据；`execute` 不接收数据库会话或 ORM 实例；完成后执行器单独写回。
3. **自动发送按目标和源消息 ID 去重。** 已排队、等待下载、发送中及成功记录都参与去重。手动提交表示用户主动要求再次发送。
4. **数据库租约与真实操作生命周期分别负责恢复和资源安全。** 租约用于判断任务归属，`MediaRuntime` 用于记录当前进程仍在执行的真实操作。租约过期不能直接证明文件已无人使用。
5. **取消后必须收回实际操作。** `run_blocking` 在取消时等待 SDK、CLI 或磁盘调用退出，再传播取消。多次取消也不能把线程遗留在后台。占用保留期间，其他执行器不能领取同一任务，清理不能删除其文件。
6. **所有文件删除遵守同一占用规则。** 手动清理在两个数据库事务和磁盘删除期间持有清理保护；缓存定时清理同时检查实际操作和持久化待发送任务。下载、发送、归档使用相同的操作登记。

## 发送状态

- `queued`：已持久化，等待执行；手动接口返回“已加入发送队列”。
- `sending`：短事务领取后，由执行器负责发送和续租。
- `waiting_download`：引用发送不可用，等待已安排的图片、视频采集完成。
- `success` / `failed`：终态，具体结果在发送记录中查看。

`forward_mode` 保存原生隐藏转发或清洗复制模式；`delivery_stage` 保存引用发送或本地补发阶段。阶段与执行状态分开保存，避免 `sending` 被重启恢复时丢失原来正在执行的步骤。失败记录不无限自动重发，用户可处理素材后手动提交新任务。

领取下载和归档任务时跳过其他事务正锁定的消息，避免一个忙碌消息堵住整个队列。自动转发执行前检查当前规则和账号监听状态；手动转发无需启动监听。两种方式共同检查发送账号和目标状态。

## 部署与恢复边界

沿用原业务数据库和 Redis；没有新增队列服务、独立数据库或新的后台进程。现有后台任务包含发送、下载和归档三个执行通道。`ARCHIVE_ENABLED=false` 只关闭采集、补采及云端归档，发送执行器仍运行。

涉及本地采集文件的部署继续要求 `APP_WORKERS=1`、`APP_RELOAD=false`，同一素材目录和 Telegram session 不运行多个服务实例。进程内操作登记依赖这个已有约束，不能据此宣称支持分布式多副本。

源码部署先备份数据库、停止旧后端，执行 `APP_ENV=prod ../.venv/bin/python -m alembic upgrade head` 到 `20261114_01`，再启动。`20261112_01` 补齐租约、发送模式及阶段，保留历史结果，并把旧待补发记录标记为本地阶段；`20261114_01` 增加归档格式和成员表，历史任务回填为单成员、逐文件归档。已有 ZIP 任务时禁止回退该迁移，避免丢失成员关系。

无法强制取消的 SDK 调用会延迟正常停止，直至调用完成或自身超时。这是显式等待真实操作退出；不是把未结束的上传交给另一个任务重试。

发送成功与数据库提交之间仍存在外部系统事务间隙：进程恰好在两者之间崩溃时，恢复可能重复发送。当前不承诺 Telegram 的 exactly-once。云端适配器在重试前核对已上传文件；夸克按目录、文件名和大小核对，S3 还核对 SHA-256 元信息。真实供应商链路仍需目标服务器验收。

## 单条与批量 ZIP 归档

一次提交对应一个 `tg_archive_task`，所选消息及其素材版本保存在 `tg_archive_message`。任务上的 `message_id` 仅作为队列领取的锁定锚点；归档状态查询、本地清理保护、重试检查和实际操作登记都覆盖全部成员。新增素材只影响该成员的最新归档状态，不改写既有 ZIP 清单。

提交事务按消息主键顺序锁定成员，验证素材就绪，按发送时间及源消息 ID 固定包内顺序，并保存每项素材的名称、大小和 SHA-256。`tg_archive_item` 同时记录不可变的源素材清单与一个 ZIP 输出项。打包使用有界缓冲，边读取边校验源内容；固定时间戳和 ZIP 存储模式使失败或重启后重建的文件保持一致。上传成功后校验租约，在同一事务完成整个任务及其输出记录。

ZIP 临时文件只属于当前任务的一次尝试，结束时删除；中断重试重新生成，原始素材仍由用户手动清理。整个打包、上传和临时清理期间，`MediaRuntime` 登记全部成员；取消时等待真实线程退出后才释放占用。磁盘不足沿用现有暂停和自动重试机制。

`archive_format=files` 的历史任务继续由 `_archive_files` 处理，维持原来的目录和已上传项；新提交只走 ZIP 流程。保留旧路径是为了历史未完成任务仍可重试，待不再需要重试这些任务后可移除。

## 验证

`tests/test_delivery_pipeline.py` 覆盖事务回滚、提交前不发送、手动/自动统一执行、源引用和本地回退、相册完整性、原生转发、清洗与目标广告、实际 PostgreSQL 并发，以及上传取消后等待退出。

`tests/test_forward_leases.py` 覆盖续租、租约丢失、重启恢复、旧任务不能覆盖新任务、混合缓存保留和真实数据库行锁。已有素材归档、权限、清理和夸克测试继续覆盖周边契约。旧的同步发送方法及针对这些方法的测试已移除，相应行为改由真实任务流程的集成测试验证。

`tests/test_zip_archive.py` 及 `tests/test_media_archive.py` 覆盖单批次单 ZIP、成员顺序和重名、失败后确定性重建、所有成员的归档状态与清理保护、源文件校验和空间不足、名称冲突，以及历史任务与数据库迁移兼容。
